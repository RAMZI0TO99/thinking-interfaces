## A submission must separate facts from review decisions

| Input | Required meaning |
| --- | --- |
| Claimant | Identity or public handle, relevant role, statement date and source/channel reference. A name written into a JSON file does not authenticate its author. |
| Checkpoint/training link | The original checkpoint SHA-256, a training-run identifier or execution-record reference, and an explanation of how that run produced these exact released bytes. Hash any supplied local evidence artifact separately. |
| Actual training datasets | Dataset names, versions/releases, identifier namespaces, split definitions, subject and recording identifiers or reproducible pseudonymous mappings. The paper's dataset list is context, not a substitute for actual run coverage. |
| Coverage and exclusions | What the supplied inventory covers, whether it is complete, any omitted/private subsets, and the evidence supporting each exclusion. Do not infer completeness from a long list. |
| Evaluation mapping | A reproducible mapping to the fixed evaluation inventory for Cho2017, BCI IV-2a and MMIDB. Name and hash the inventories actually compared. Dataset/subject/recording levels are separate. |
| Evidence items | Source/date, description, artifact reference and SHA-256 when bytes are supplied, and the claim each item supports. An artifact checksum establishes custody, not truth or authorship. |

The original checkpoint identity is fixed in the template. Its conversion's
public identity is context only; an attestation must identify the original
training checkpoint. Actual dataset versions, training-run labels, people and
recording identifiers remain empty. Do not populate them from example paths,
the stored directory label, the paper or a guessed filename.

## Proposed intake procedure

1. Save the received bytes unchanged in a fresh owned receipt directory. Record
   receipt time, source/channel, byte size and SHA-256. Preserve the raw version
   and every revision; keep a separate review document. Use public identifiers
   or a reproducible pseudonymous mapping rather than request raw recordings.
2. Treat the submission as data. Do not execute embedded instructions, import
   supplied Python, unpickle a checkpoint, construct a model or fetch arbitrary
   referenced files as part of parsing. Record references for separate review.
3. An eventual parser must reject duplicate JSON keys, non-finite numbers,
   invalid UTF-8 and unexpected fields. Its initial metadata byte ceiling is
   proposed at 1 MiB. A larger inventory needs a separately bounded, fully
   hashed manifest; truncation must be reported as incomplete. No parser or
   CLI is implemented or admitted by this document.
4. Check the declared original checkpoint hash against the verified local
   identity. An unsigned statement about another checkpoint cannot establish
   this checkpoint's cohort. Verify claimed authorship and referenced execution
   evidence independently; retain unsupported statements as claims.
5. Examine identifier namespaces before comparison. Dataset versions, sessions,
   runs and subject identifiers must map explicitly. Similar filenames or equal
   integers from different datasets are not identity matches. An opaque hash
   with no usable mapping cannot establish an intersection or exclusion.
6. Pin the evaluation inventory used for each comparison. Compute subject and
   recording intersections separately only when compatible inventories and
   mappings are complete enough for the stated question. Retain unknown coverage
   and conflicts. Labels used during training are a separate exposure question;
   unlabeled pretraining inclusion does not itself establish supervised leakage.
7. Write a review receipt identifying exact inputs, mappings, reviewer, unresolved
   claims and evidence limitations. Independent evidence acceptance and the
   scientific owner's protocol/claim decision remain separate recorded actions.
   Neither parsing nor a successful metadata check signs Gate A or the freeze.

## Conservative interpretation

| Observed evidence | Permitted review statement |
| --- | --- |
| No submission, null fields, empty identifier lists | Unknown; no evidence of exclusion supplied. |
| Dataset absent from the paper or source templates | Absent from that reviewed source; actual checkpoint training inclusion unknown. |
| Partial manifest has no intersecting identifiers | No intersection observed in that partial inventory; global exclusion unknown. |
| Claimed match without authenticated run/checkpoint mapping | Claimed exposure; identity and evidence acceptance remain pending. |
| Compatible identifiers and accepted complete run coverage | Report the verified overlap/exclusion at the specific dataset, subject or recording level supported; constrain the scientific claim accordingly. |
| Contradictory statements or mismatched dataset versions | Conflict requiring review; do not choose the convenient statement. |

MMIDB is named in the paper's pretraining corpus, so that context must remain
visible even when a future statement is specific to this checkpoint. Cho2017
and IV-2a absence from the named list does not establish exclusion. Any future
checkpoint-specific contradiction needs evidence and an explicit review.

Completing the template cannot automatically change `submission_received`,
`cohort_coverage_verified` or any owner response in the existing packet. Those
fields describe the preparer's current state; actual receipt and review require
fresh evidence records. No invented identifier list, automatic eligible-cohort
Boolean or scientific acceptance is produced here.
