# Project execution policy

Effective 28 October 2026, Asia/Riyadh, under the owner's direct instruction.
This is the current operational policy for Thinking Interfaces.

## Authority and scheduling

The owner sets scope and scientific decisions. The project Root manages
implementation, scheduling, review and operational admission within that scope.
All active work is organized within this project. Do not contact, poll or wake
other project chats for scheduling or permission unless the owner later asks.

Earlier requirements for outside acknowledgements, shared scheduling windows,
externally issued decisions and outside pause files are superseded for future
work. They remain only in historical evidence. They are not prerequisites for
documentation, design, implementation, review or locally admitted validation.
No new confirmation of this workflow choice is needed.

Document-only work uses file, text, link and hash inspection. It does not need
a compute lease, runtime bootstrap or project test execution.

## Same-project collaboration

Root assigns explicit file ownership and preserves other agents' changes.
Use Root plus one implementation author or one independent reviewer at a time
for the current bounded work. Reviewers must not certify their own code.
Record review findings and their resolution in this project's phase records.
A completed source review does not prove runtime behavior.

## Local run admission

Before a validation or engineering operation, Root records:

1. The bounded purpose, exact source and runtime pins, and independent source review.
2. An unused attempt/output directory, allowed commands, expected artifacts and
   explicit refusal conditions.
3. Current available resources and the applicable time, memory, disk, thread and
   device limits; a local stop mechanism controlled by the owner or Root.
4. Owned process/Job containment, cleanup obligations and complete caller-return
   evidence, followed by independent review of the actual saved results.

Use a newly reviewed, versioned runner compatible with this policy. Do not
fabricate legacy decision files, satisfy old dependencies with dummy tokens,
rewrite old receipts or launch a frozen script under an incompatible contract.
The old contracts remain inert records. A successor must explicitly replace
obsolete scheduling dependencies while retaining the substantive guards.

For the pending nonnumerical metadata/profile and telemetry phase, the owner's
existing available-memory amendment remains applicable: startup 4 GiB, active
4 GiB and free disk 20 GiB, with the previously scoped native time/memory caps,
one CPU/Torch thread and hidden GPUs. Do not ask the owner to repeat that choice.
Observe current availability before execution. The unit limit remains 600
seconds with 4096/5120 MiB process/Job caps; external closeout has its separately
bounded caller. New workloads require their own explicit resource envelope;
this policy does not expand a phase-specific amendment.

A stop request or failed resource/custody predicate stops the owned operation
under its reviewed cleanup procedure. Never kill unrelated processes, clear
shared caches or silently retry a consumed attempt.
